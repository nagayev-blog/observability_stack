# Observability-стек: метрики и логи для проектов в Portainer + Traefik

Саммери проекта по развёртыванию системы сбора метрик и логов. Включает не только итоговые решения, но и рассуждения, развилки и компромиссы, на которых эти решения принимались.

---

## 1. Исходная задача

Собирать метрики и логи со своих проектов (Python, направление highload / AI / MAS), развёрнутых через стеки в Portainer + Traefik на нескольких хостах. Базовый выбор инструментов — Prometheus/VictoriaMetrics + Loki + Grafana.

Ключевые ограничения, которые всплыли по ходу:
- Нет файлового доступа к хостам (изначально рассматривали S3 + wget для доставки конфигов).
- Проекты живут в отдельных стеках, но все в одной сети `traefik_default`.
- 2-3 хоста, которые нужно мониторить.

---

## 2. Фундаментальная модель: pull vs push (главный концептуальный блок)

Большая часть разговора ушла на понимание того, **как вообще работают метрики**. Это важнее, чем конкретные конфиги, поэтому фиксирую подробно.

### Метрики живут в памяти процесса

Метрика — это обычная переменная в RAM приложения (`Counter`, `Gauge`, `Histogram` из `prometheus_client`). Ничем принципиально не отличается от любого `counter += 1` в бизнес-логике. Библиотека добавляет лишь реестр (registry), куда метрики регистрируются, и функцию рендеринга в текстовый формат.

### Эндпоинт `/metrics` ничего не копит

`/metrics` — это **не хранилище и не буфер**. В момент HTTP-запроса библиотека берёт текущие значения из памяти и рендерит в текст. Между запросами там ничего не накапливается. Это всегда **снимок текущего состояния**, а не история.

### Pull-модель: Prometheus сам ходит за данными

Prometheus периодически делает `GET /metrics` и забирает снимок. Приложение — пассивный источник, оно про Prometheus ничего не знает. Связь слабая и однонаправленная: список «кого скрейпить» знает только Prometheus.

### Ключевые следствия (мои вопросы → ответы)

- **«Метрики копятся в /metrics, в памяти или в файлах?»** — В памяти процесса. `/metrics` ничего не копит, это живой снимок. История хранится у Prometheus в его TSDB на диске.

- **«Если Prometheus не забирает 10 минут — не закончится ли память?»** — Нет. Counter/Gauge — это фиксированные переменные, `inc()` миллион раз не меняет объём памяти. Скрейп — это операция чтения, его отсутствие ничего не накапливает. Память растёт **только** от создания новых серий (новых комбинаций лейблов), и это не зависит от интервала скрейпа.

- **Что теряется при простое скрейпа** — не память, а **разрешение истории**. Counter покажет накопленную сумму корректно (rate это учтёт), но промежуточные значения и пики Gauge между скрейпами теряются. Разрешение данных = частота скрейпа.

- **Рестарт приложения обнуляет счётчики** — это нормально, Prometheus умеет детектировать сброс. Персистить счётчики в файл — антипаттерн.

- **Главная ловушка — кардинальность лейблов.** Лейблы только для ограниченных множеств (статусы, типы задач, имена агентов). Лейбл с `user_id` / `request_id` / timestamp создаёт миллионы серий и кладёт и приложение, и хранилище. Это та же ошибка, что бесконтрольно растущий dict в обычном коде.

### Итоговая ментальная модель (моя формулировка, которую подтвердили)

Решение спроектировано так, что **приложение автономно в текущей работе** (ведёт учёт в памяти само для себя, не зависит от наличия Prometheus), а **Prometheus автономен как архив** (хранит историю у себя). Один без другого работает; полную картину «состояние + история» даёт связка. Метрики — это несколько дешёвых переменных в процессе, а весь «вес» (хранение, история, диск) вынесен наружу.

## 3. Как приложение публикует метрики

Pull-модель требует, чтобы приложение отдавало `/metrics`. Дописать нужно немного.

**Приложение без веб-сервера (воркер, MAS-агент):**
```python
from prometheus_client import start_http_server, Counter
start_http_server(8000)   # поднимает /metrics в фоновом потоке
```

**Приложение на FastAPI/Flask** — встроить эндпоинт в существующий сервер (или `prometheus_fastapi_instrumentator`), не поднимать второй порт.

**Логи — кода не требуют вообще.** Promtail/Alloy читают stdout/stderr контейнера. Достаточно логировать в stdout (дефолт для Python `logging`/`print`).

Минимальный полезный набор метрик для агента/сервиса: `requests_total` (по статусу), `request_seconds` (гистограмма латентности), `in_flight` (gauge текущей нагрузки), `queue_size` (gauge очереди), `errors_total` (по типу).

**Multiprocess (Gunicorn, multiprocessing)** — единственный случай, когда метрики временно пишутся в файлы (`PROMETHEUS_MULTIPROC_DIR`) как механизм обмена между процессами. Актуально для highload — отметить на будущее.

## 4. Метрики vs логи — разделение ролей

- **Метрики** (VictoriaMetrics) — числовые временные ряды. Отвечают на вопрос «**что** происходит»: очередь растёт, латентность скачет, ошибки полезли. Требуют кода.
- **Логи** (Loki) — текст из stdout. Дают контекст. Кода не требуют.
- **Трейсы** (будущее, OTel) — путь одной задачи через цепочку сервисов. Отвечают на «**где** именно теряется время». Метрики структурно на это не отвечают.

Типы метрик = типы вопросов:
- **Counter** — «сколько всего случилось» (только растёт). Смотрят не значение, а `rate()`.
- **Gauge** — «сколько прямо сейчас» (растёт/падает). Главный индикатор здоровья (размер очереди, живые агенты).
- **Histogram** — «как распределяются значения» (латентность, перцентили p95/p99). Среднее врёт — прячет хвосты; p95/p99 показывают «как плохо невезучим». Критично для highload.

Пример детективной ценности (ночной инцидент): история метрик читается как причинно-следственная цепочка — GPU OOM → агенты падают → очередь распухает → латентность взлетает. Корень виден за 30 секунд.

## 5. Дискретизация и retention — кто и что настраивает

Разбирали три уровня плотности данных:

1. **`scrape_interval`** (Prometheus → приложение) — реальная плотность сырых данных, физический предел разрешения. Событие между скрейпами не существует в данных.
2. **TSDB** — хранит сырые точки с шагом `scrape_interval`. Grafana видит **только их**, не приложение.
3. **`step` запроса** (Grafana → хранилище) — Grafana подбирает шаг под ширину панели. Когда `step` крупнее `scrape_interval`, сырые точки сворачиваются — и **как** именно сворачиваются, определяет PromQL-функция (`rate`, `avg_over_time`, `max_over_time`), а не Grafana. Отсюда эффект «пик на дневном графике есть, на месячном пропал» — не потеря данных, а укрупнение step без правильной агрегирующей функции.

**Retention и глубину настраивает хранилище, НЕ приложение** (у приложения нет истории, нечего удерживать):
- `--retentionPeriod` / `--storage.tsdb.retention.time` — горизонт назад.
- `scrape_interval` — плотность точек.
- Единственное «временно́е» решение в коде — **границы корзин гистограммы** (`buckets`). Их Prometheus не восстановит задним числом; грубые корзины = неточные перцентили навсегда. Но это про гранулярность измерения, не про retention.

Для highload на вырост: Thanos / VictoriaMetrics / Mimir — долгое хранение в S3 + downsampling старых данных. Слой над/вместо Prometheus, приложение не меняется.

## 6. Push в TSDB — развилка вариантов

Вопрос «можно ли пушить метрики» разобрали с компромиссами:

- **Pushgateway** — официальный, но узкая ниша: короткоживущие batch/cron-задачи, которые умрут раньше скрейпа. **НЕ для долгоживущих сервисов**: не имеет retention, хранит только последнее значение, оно «залипает навсегда» после смерти приложения. Антипаттерн для MAS-агентов.
- **Remote Write** — настоящий push потока сэмплов в хранилище. Принимается специализированными TSDB.
- **VictoriaMetrics** — Prometheus-совместимая TSDB, умеет и pull, и push (remote write, Influx, Graphite, OpenTSDB). Экономнее по памяти/диску, лучше держит высокую кардинальность (важно для MAS), масштабируется в кластер.
- **OpenTelemetry** — вендор-нейтральный SDK, push в Collector, объединяет метрики + логи + трейсы. Выше сложность, но для MAS трейсинг часто ценнее метрик.

**Главный трейдофф push vs pull:** push возвращает проблему буферизации. Если приёмник недоступен — клиент копит данные в памяти/на диске (вот тут страх про переполнение памяти становится реальным, в отличие от pull). Нужны лимиты буфера, backpressure, дроп. Плюс с push теряется бесплатный сигнал «приложение не отвечает на скрейп = упало».

## 7. Выбор стека: эволюционный путь (ключевое рассуждение)

Договорились о поэтапном подходе — **усложнять под реальную потребность, а не авансом**. Задача делится на два этапа: (1) развернуть хранилище + Grafana, (2) налаживать сбор, наращивая по мере углубления.

Триггеры перехода — не «вообще усложнить», а конкретные упёршиеся потребности:
- Упёрся в хранение/кардинальность → **VictoriaMetrics** (миграция с Prometheus почти бесплатна: тот же PromQL, дашборды, код).
- «Вижу что плохо, но не вижу где» → **OTel-трейсинг**.
- Нужны логи рядом с метриками → **Loki**.

### Prometheus vs VictoriaMetrics

Выбор не критичен на старте (миграция бесплатна), но VM выбрали сразу. Причина: по развёртыванию VM местами **проще** — single-вариант запускается без конфиг-файла, настройки флагами (`--retentionPeriod`, `--httpListenAddr`), что снимало боль с отсутствием файлового доступа. Нюанс: список таргетов всё равно где-то нужен (либо VM сама скрейпит с `--promscrape.config`, либо отдельный `vmagent`).

### OTel vs VictoriaMetrics — это разные слои, не конкуренты

- **OTel** — слой инструментирования и доставки (замена `prometheus_client` + Collector).
- **VictoriaMetrics** — слой хранения (замена Prometheus).
- Типовая связка: OTel инструментирует → шлёт в VictoriaMetrics.

Порог входа (Prometheus = 1): VM поверх знания Prometheus ≈ 0.2; OTel только метрики ≈ 1.5; OTel полноценно (Collector + трейсы + context propagation) ≈ 3-4. OTel сложнее: свой словарь (signals, resource, exporters, context propagation), отдельный Collector, push по умолчанию. Но для MAS трейсинг — родная территория OTel, и хорошей чисто-Prometheus альтернативы ему нет.

## 8. Агент сбора: vmagent vs Grafana Alloy

### Выбор паттерна

Сайдкар/агент-на-хост — индустриальный стандарт. Код приложения остаётся чистым (отдаёт стандартный `/metrics`), а способ доставки становится заменяемым инфраструктурным решением. Точка сопряжения — стабильный текстовый формат `/metrics`, не код. Можно менять сборщик, не пересобирая проекты.

### vmagent

Лёгкий, родной для VM, ест знакомый прометеевский `scrape.yml`. Минус: только метрики — для логов нужен отдельный Promtail, для трейсов ещё что-то.

### Alloy (выбрали его)

Единый агент: метрики + логи + трейсы. Один контейнер на хост вместо пары vmagent + Promtail. Встроенный OTLP-приёмник = задел под будущий трейсинг для MAS.

**Трейдоффы Alloy:**
- (−) Свой язык конфига (River / Alloy syntax) — компонентно-потоковая модель с `forward_to`, не прометеевский YAML. Выше порог входа.
- (−) Тяжелее vmagent.
- (−) Философское трение стеков: хранилище от VictoriaMetrics + агент от Grafana. Рабочий гибрид (совместимы по remote write), но теряется часть бесшовности родной связки vmagent ↔ VM.
- (+) Заменяет два агента сразу, готов к трём сигналам.

**Логика выбора:** ценю чистую архитектуру + мечу в трейсинг для MAS → один раз вложиться в язык Alloy и получить единый агент на годы, вместо доустановки третьего агента под трейсы позже. Переход на Alloy с vmagent не разрушает ничего (хранилище и Grafana те же).

### Alloy заменяет и Promtail

Promtail формально переведён в режим поддержки в пользу Alloy. Так что Alloy = vmagent + Promtail в одном.

## 9. Топология: один агент на хост

vmagent/Alloy/Promtail видят **только контейнеры своего хоста**:
- Метрики — Alloy ходит по HTTP на `/metrics` контейнеров своей Docker-сети.
- Логи — Alloy/Promtail читают файлы Docker-логов с **локального диска** хоста (`/var/lib/docker/containers/...`), по сети к чужим хостам не дотянуться.

Зеркальная модель:
```
МЕТРИКИ:  контейнер /metrics ──HTTP pull──► Alloy ──push──► VictoriaMetrics
ЛОГИ:     контейнер stdout ──файл на диске──► Alloy ──push──► Loki
```

Поэтому на **каждом хосте** — свой Alloy, все пушат в одну центральную пару VM + Loki. Тяжёлая часть (VM + Loki + Grafana) — на одном «центральном» хосте; на каждом хосте — лёгкий сборщик.

## 10. Связь между хостами — трейдофф безопасности

Проблема: «наружу только Grafana» работает лишь на одном хосте. Alloy с другого хоста не достанет VM/Loki по внутренним именам (Docker-сети между хостами не связаны без Swarm overlay).

Варианты (от худшего к лучшему):
1. **Публикация VM/Loki наружу + токен** (выбрали для скорости). VM/Loki не имеют своей аутентификации → закрыли basic-auth на Traefik. Компромисс: эндпоинт записи в интернете.
2. **VPN/Tailscale** (правильный путь). Приватная mesh-сеть, Alloy пушит по `100.x.x.x`, наружу только Grafana. Рекомендованная цель для миграции. Переход = смена URL в конфиге Alloy.
3. **Docker Swarm overlay** — растягивает сеть между хостами, но меняет модель эксплуатации. Не выбрали.
4. **VM на каждом хосте + федерация** — избыточно для масштаба.

**Выбор: вариант 1 сейчас, миграция на Tailscale потом** (меняется только URL).

## 11. Что развёрнуто — итоговая архитектура

### Серверный стек (только на хосте `dckr`)

VictoriaMetrics + Loki + Grafana, всё за Traefik.

- **Домены наружу:** `grafana.example.com` (вход), `vm01.example.com` и `loki01.example.com` (приём данных, закрыты basic-auth).
- **VM:** retention 3 месяца, порт 8428, basic-auth middleware `ingest-auth`.
- **Loki:** конфиг встроен через Docker `configs` (inline в compose), retention 720h.
- **Grafana:** логин/пароль из env.
- **Учётки в env-переменных:** `GF_ADMIN_USER`, `GF_ADMIN_PASSWORD`, `INGEST_AUTH`.
- **Конфиги через Docker `configs` inline** — не S3. Безопасно (нет секретов), нет зависимости от внешнего хранилища при рестарте.

### Стек Alloy (на хосте `dckr`)

- Подключён к `traefik_default` (одна сеть — там уже все контейнеры + VM/Loki). Сеть `monitoring` оказалась лишней сущностью: VM/Loki и так в `traefik_default` ради публикации, отдельная сеть ничего не изолировала.
- Пушит во внутренние имена `http://victoriametrics:8428` и `http://loki:3100` **без токена** (контейнер-контейнер по Docker DNS, минуя Traefik). Токен нужен только агентам с других хостов через публичные домены.
- UI на порту 12345 (временно опубликован для отладки, убрать потом).
- Доступ к `/var/run/docker.sock:ro` для Docker service discovery.

### Развязка по лейблам

- `monitoring.scrape=true` + `monitoring.port=<порт>` → собираются **метрики**.
- `monitoring.logs=true` → собираются **логи** (порт не нужен — логи из stdout).
- Хочешь оба — все три лейбла.
- `action: keep` по лейблу обязателен: в `traefik_default` лежат ВСЕ контейнеры, без фильтра Alloy долбился бы в `/metrics` тех, у кого его нет.

### Кардинальность в Loki

Та же дисциплина, что в метриках: лейблы Loki — это индекс. Не делать лейблами высококардинальные значения (request_id, user_id) — убьёт производительность. Лейблы для ограниченных множеств; уникальное содержимое ищется полнотекстово внутри потока.

## 12. Настройка учёток (basic-auth через env)

1. Сгенерировать пароль-токен: `openssl rand -hex 24`.
2. Сгенерировать хеш: `htpasswd -nbB ingest 'пароль'` (`-B` = bcrypt).
3. **Удвоить каждый `$`** в полученной строке (`$2y$` → `$$2y$$`) — и это удвоенное значение целиком положить в env-переменную `INGEST_AUTH`. Удвоение нужно в **значении переменной**, в compose стоит чистый `${INGEST_AUTH}`.
4. Агентам (другие хосты) — пароль в открытом виде в `basic_auth { password }`.

Проверка: `https://vm01.example.com` должен спрашивать логин/пароль. Если пускает без запроса или 500 — хеш побился на экранировании.

## 13. Грабли, на которые наступили

### Docker `configs` иммутабельны

Главная засада сессии. `configs` (и `secrets`) **не обновляются** при обычном «Update the stack» — Docker переиспользует старый объект с тем же именем, даже если содержимое в compose изменилось. Контейнер новый, конфиг внутри — старый.

**Симптом:** правил конфиг Alloy (лейбл логов `monitoring.scrape` → `monitoring.logs`), редеплоил, но запущенный Alloy продолжал фильтровать по старому `monitoring.scrape`. Логи keycloak (помеченного `monitoring.logs=true`) не собирались, т.к. `keep`-фильтр их отбрасывал. Цепочка обрывалась между `discovery.relabel.logs` (на входе все контейнеры, на выходе пусто) и `loki.source.docker` (`targets [ ]`).

**Решение сейчас:** удалить контейнер и создать заново (удаляется и объект конфига).

**Решение на будущее:** версионировать имя конфига (`alloy_config_v2` → `_v3` при правках) — Docker увидит новое имя и пересоздаст объект. Либо bind-mount файла (но не было файлового доступа).

### Диагностика через UI Alloy

UI на порту 12345 — главное место отладки.
